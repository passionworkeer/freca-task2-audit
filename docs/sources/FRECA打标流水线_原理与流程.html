FRECA 41CP 打标流水线 — 原理与流程全解

从法规 PDF + 农场证据包，到 100 案例 × 41 检查点 = 4100 个合规判定的完整链路。三个核心问题：评分标准怎么定、证据怎么处理、格子怎么打。

4,100判定格（100 case × 41 CP）
7 分钟全量运行（100 并发）
0 / 1 / N/A判定值域
73%与人工核验一致率（37 格样本）

1评分标准是怎么制定的

核心思路：评分标准不是一次生成的，而是「LLM 起草 → 人工多轮修正 → 材料增补 → 双来源合并」逐步收敛的过程。最终形态是 41 行的 Excel，每行 = CP定义 + 红线 + 评分标准全文（含门槛材料）。

1.1 演进时间线（v4 → v4.1 → v4.2 → 最终合并版）

v4 初版：LLM 全文喂起草 翻车

把约 25,000 字符的法规全文直接塞给 LLM，让其为每个 CP 生成评分标准。结果：早期 CP「范围过宽」——CP1 的标准把相邻 CP（暂停/设施/记录）的内容全部写进去，一个 CP 的标准可以判半个法规。

评审发现：系统性范围过宽 诊断

对 CP1-14 逐条对照红线表评审：✅ 8 个合格、❌ CP1 严重过宽、⚠️ CP3/4/5/6 越界。根因是全文喂让 LLM 写出了"通用标准"而非"本 CP 专属标准"。

v4.1 修正：策展条款 + 范围约束 方法论

两招收敛：① 策展条款——人工精选该 CP 直接依据的条款（如 CP1 只喂 s1-6/s2-4 item2/s4-1/s4-5/s11-7），不再全文喂；② 范围约束 prompt——硬性写明"必须排除、属于其它 CP 的内容"。并用检索召回做了覆盖率审计，确认策展没有漏。

用户编辑轮：边界彻底收敛 人工修正

CP1-14 经一轮人工编辑：CP6 弃用"Act s120 变通"改用 Act s146/s147 通知义务（经 AustLII 原文核验）；CP12 独占"注册暂停"判定；CP8-14 收窄为"一 CP 管一款"（照明→CP9、洗手→CP10、清洁→CP11……），消除 CP 间重叠。

v4.2：门槛/依据材料增补 自足性

引入"门槛判定"概念——判官先判"这批货是不是规定货物"（s1-6/s2-1/s1-7/s2-2），再判"作业是否在注册范围内"。补齐 s2-4 表 item2、s4-18/4-19（暂停）、s4-16/4-17（变更）等全部判定所需材料，并确立三来源原则：每个判定条件必须能回溯到 CP定义 / CP红线 / 法规内容之一，否则删除或标注"判定解释"。

最终合并版：双来源汇合 交付

CP1-14 取 HTML v4.2（最收敛版本，门槛材料并入评分标准）；CP15-41 取团队核验文件的修正版（列16），原版兜底；CP27 两批核验结论冲突时取更严格版。产出 41 行 × 6 列的《最终合并版·材料并入.xlsx》——这就是打标流程的评分标准输入。

1.2 最终评分标准的结构（每个 CP 的 prompt 输入）

组成部分内容在打标流程中的角色
CP定义(中)要素名 + 检查点定义（如 1.2 Plans and specifications）告诉判官"查什么"
红线R3(中)官方判定命题的中文翻译判定命题——"判什么成立"
评分标准（最终版·含门槛/依据材料）合规条件 / 不合规条件 / N/A 条件 + 门槛判定材料（如规定货物认定清单）+ 术语定义 + CP 边界说明判定规则的主体——"怎么判"
Act层参考（联网核验）Act s12/s146/s147 等不喂——保持零联网依赖，仅人工溯源用

2证据侧是怎么处理的

核心思路：证据不是原样喂，而是「Docling 解析 → 四道过滤器净化 → 段落级语料库 → 按 CP 检索片段」。每一段语料都可追溯来源文件。

2.1 处理链

Docling 解析（一次性）99 case × 9 文件 → 完整 markdown（表格保真），按 case 落盘缓存 + 文件指纹校验。改用完整原文而非切分 chunk（用户要求）。
→
署名过滤按《文件署名整理表》剔除"外来农场"文件的段落——治理数据集的跨农场文件污染（98% case 至少混入 1 份）。
→
样板净化剔除 docling 提取的法规引用样板段（*Rules sX-X*）、纯标题段、页眉黑名单段。
→
段落语料库每段带 [T{track}] 前缀（判官可追溯来源），缓存复用（每 case 一次构建，41 格共用）。

2.2 为什么这样处理（两个翻车教训）

教训现象对策
全文喂 × 署名污染 = 0 爆炸初版把 9 文件全文（约 12 万字符）全喂给 LLM，混入的别家农场文件（RE 号/农场名不符）被当成"该农场证据体系混乱"，3444 个 0 判定中 82% 的理由是"证据不一致"，28 个 CP 对全部 100 case 判 0改为检索片段喂法 + 署名过滤
检索 query 污染query 混入评分标准全文后，establishment/record 等通用法规词把真正判别性的段落挤出 top-N，导致"证据里有照明数据却检索不到"query 只用英文红线 R3（官方判定命题，判别性最强）
双农场特例：RE-WA-2021-0077 母卷含两个农场各 9 文件，拆成 F100/F35 两个审计单元（凑满 100 case）；拆分单元内文件已按农场物理拆开，不再做署名二次过滤。

3最后是怎么打标的

核心思路：「一次运行 = 一个格子」。每个格子独立完成「检索 → 组装 prompt → LLM 判定 → 落盘」，4100 次独立运行由调度器编排。

3.1 单格判定（打标原子操作）

① 检索query = 该 CP 的英文红线 R3（官方判定命题，判别性最强）。BM25 变体：IDF 加权 + 停用词剔除 + 段落长度归一化 → top-14 相关片段。
→
② 组装 promptSYSTEM：中文审计员角色 + N/A 从严规则（证据不足≠N/A，无法证明合规=0）。USER：CP 评分标准全文 + top-14 片段。仅 4-7K 字符。
→
③ LLM 判定deepseek-v4-flash，temperature=0，非思考模式 → 严格 JSON：{verdict: 1|0|N/A, conclusion, clauses[], evidence[]}。
→
④ 落盘{RE}_{CP}.json 独立缓存——断点续跑的原子单位。

3.2 判定三值的语义（严格定义）

值语义触发条件
1合规满足评分标准全部合规条件，且不命中任何不合规条件
0不合规命中任一不合规条件；或合规条件未满足；或证据不足无法证明合规（评分标准无"缺失判 N/A"条款时）
N/A不适用仅当评分标准明确列出的 N/A 条件成立（如非规定货物、无出口作业区域）——证据不足不得判 N/A

3.3 调度（4100 次运行的编排）

任务编排
  • 100 case（98 单 + 双农场拆 2）× 41 CP = 4100 格
  • shuffle 打散 → 轮转切 10 批（每批约 410）
  • 每批 ThreadPoolExecutor 并发（实测 100 并发最稳；410 会打崩代理）
  • AdaptiveLimiter：429 自动降并发档位
  • 失败重试 3 次 + 指数退避；失败清单落盘，重跑只补缺
输出交付
  • 矩阵表：101 行 × 42 列（RE Number + CP1-41），对齐提交模板
  • 理由明细：4100 行（verdict / 结论 / 命中条款 / 证据引用 / tokens）
  • 全量实测 7 分钟；v6 分布 0=78% / 1=20.5% / N/A=1.7%

4质量验证与已知边界

打标不是跑完就算——冒烟、全量、人工核验三层验证，残留问题如实列出。
验证层结果
冒烟单格抽样（含全 0 CP 复测），确认检索召回与判定理由合理后才全量
全量覆盖4100/4100 全覆盖，0 失败（两轮补齐）
分布体检全判 0 的 CP 从 26 个降到 8 个；1 占比 5%→20.5%
人工核验5 案例 × 9 重点 CP：一致率 73%（去 CP12 后 81%）；分歧均衡（判严 5 / 判松 5），热点 CP12（阈值失准）与 S038 案例（偏松）
已知边界：① 8 个 CP 仍全 0（CP16/21/27/29/30/31/34/36），待人工判断是数据本身违规多还是仍判严；② 检索片段存在天然信息折损，人工看全文链更全面；③ 双农场行 RE 列为 F100/F35 后缀，提交前需确认官方标识符口径。
